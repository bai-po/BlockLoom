# 资源导入详细规范

本标准用于 OXAL MC Studio 后续资源导入开发。以已经验证的天空加载为参考，统一流程、性能约束和验收方式；具体资源仍由各自的业务工具负责。

新增导入及对既有导入的修改应遵守本标准。不能适用的步骤在对应模块文档中说明原因与实测结果，不为凑齐步骤增加文件读取、复制或调度等待。
本标准不自动启用任何新业务按钮，也不要求立即改写已经工作的天空加载。

## 1. 与 Bus Skill 的边界

所有 Bus 接线统一引用 [$oxal-bus Skill](../../oxal-bus/SKILL.md)。使用接口时读其 [API 参考](../../oxal-bus/references/api.md)，涉及 Blender 入口或撤销时读 [Blender 接入参考](../../oxal-bus/references/blender.md)。

本标准只维护资源本身：身份与作用域、复用/实例化策略、读取计划、依赖可变性、拥有权、事务清理和性能验证。
资源目录扫描、源文件打开、贴图解码和网格准备应发生在实际业务需要时，不提前预加载。生命周期和调度规则由 Bus Skill 维护，不在此复制。

## 2. 每个导入先声明五件事

每个业务工具的常量或模块文档必须写明：

1. `asset_id`：稳定的逻辑身份，如 `oxal.sky.main`，独立于显示名和文件名。
2. `asset_version`：模板/接口版本。版本不兼容时不得悄悄复用。
3. `policy`：下表中的导入策略。
4. `scope`：复用或拥有权属于当前场景、某个实例还是整个工程。
5. `source`：随包源文件及要请求的入口数据，来源记录与哈希在制作/打包时核验。

不要为了确认资源没变化而在每次点击时计算整个文件的哈希。热路径首先判断已有资源是否完整可用。

| 策略 | 常见资源 | 再次执行的语义 |
| --- | --- | --- |
| `ACTIVATE_EXISTING` | 天空、单场景环境 | 复用这个作用域内的完整实例，再激活它 |
| `NEW_INSTANCE` | 人模、物品、道具 | 创建新的可编辑实例，不能吞掉重复导入意图 |
| `REUSE_DATABLOCK` | 材质、贴图、节点组 | 符合身份、版本、用途和可变性约定时复用数据块 |

激活类可按同目标同选项合并请求；创建实例类不能静默吞掉两次有意导入。忙碌范围依据目标、资源身份、变体与策略决定；具体状态接线引用 Bus Skill。

链接库、文件格式转换、外部文件导入等可另设策略，但必须说明语义与拥有权，不冒充普通追加。

`NEW_INSTANCE` 不代表每次都重新读源文件。可在经过验证的模板上复制实例，但必须按资源契约处理可变数据与控制器引用。
共享只读 Mesh/材质是可选优化；骨架、动作、形态键、驱动、修改器引用、灯光链接和会被业务改写的数据必须明确采用共享、复制或重映射中的哪一种。
只调用 `Object.copy()` 并不能保证所有依赖已经成为独立实例。

### 材质和其它共享依赖

方块或其它实体可引用同一份逻辑材质；不是把所有不同表面合成一个材质。共享键应覆盖资源命名空间、材质逻辑身份、兼容版本和实际影响结果的变体，例如材质包或渲染方案；显示名及 `.001` 后缀不能充当键。

- 新实例可以拥有独立 Object，同时共享允许共享的 Material、Image 或 Mesh。是否共享由依赖的可变性决定，不由实例策略一刀切。
- 用户修改共享材质会影响所有引用者；要支持实例私有调整时，显式复制相关材质/节点等可变依赖并重新绑定，不擅自修改全局共享数据。
- 不同材质块若引用同一个节点组，仍可能相互影响；复制边界必须覆盖实际会修改的依赖。
- 后续材质包功能可以按逻辑身份统一替换共享依赖，并按选定作用域重新绑定；当前未实现统一材质管理 API，不能把这个设计方向写成现成接口。
- 已接入的人模/物品栏仍按各自契约创建可编辑依赖。本规范不要求改成共享；业务授权范围以用户最新指令和 `AGENTS.md` 为准。

### 着色器节点排版

- 使用 `util/node_layout.py` 的纯视觉排版与 `util/shader_layout.py` 的实际 ID 批次适配。只调整位置、父 Frame 等视觉属性；保留业务节点名称、标签、插槽、连线、现有 Group 层级、Action/NLA 和驱动路径。业务可能使用节点标签，不能为美观重命名。
- 新导入或新建着色器由明确 EMT 业务的事务提交阶段整理，只传入本次已证明拥有的 Material/World/Light 与独立 ShaderNodeTree。不得递归整理未证明拥有的共享 Group，也不在 draw、登记、文件加载回调或无请求的 timer 中自发扫描整理；已授权请求由 EMT timer 自动推进，不改变本次事务的拥有权范围。
- 已有实例通过明确 Operator 冻结实例标识后整理，保留原生 Undo 与视觉回滚。节点界面字段参与动画或被其它 ID 的驱动读取时保留原布局并反馈，不能移动后改变业务行为。
- 历史合同仅投影工具明确生成、无业务数据的纯 UI Frame；原 Frame 与真实业务节点仍受核验。原 `location_absolute` 字段通过树上的原始 UI 记录投影到首次排版前的值，不重签业务合同，不用排版元数据替代真实参数、连线或 ID 引用。

## 3. 统一业务流程

```text
解析目标与参数
  → 按策略检查可复用资源
      ├── 命中：验证作用域/完整性 → 必要的激活或实例复制 → 返回
      └── 未命中：定位并校验源文件
                     → 合并本次读取计划
                     → 追加到未发布的暂存状态
                     → 局部准备与依赖修补
                     → 验证资源契约
                     → 提交到目标场景/实例
                     → 必要的依赖更新
                     → 返回结果

失败：恢复本次修改的既有状态 → 删除本次确认拥有的新增数据 → 交付失败回复
```

“命中”可以是激活已有资源，也可以是得到可复制的模板，含义由策略决定。
复用资源完整时，通常不要求源文件还存在。若某项业务确实还需源数据，应写明并单独验证。

### 目标和身份

- 运行期目标标识、参数快照及消息数据约定遵循 [Bus Skill](../../oxal-bus/SKILL.md)；这里另外规定资源的持久身份与拥有权。
- `session_uid` 是本次 Blender 会话内的标识，不作为跨文件保存的资源身份。持久身份可用资源标签、版本与实例 UUID 等。
- 查找优先使用维护好的直接引用、目标实例/合集内的标记和真实依赖关系。显示名只用于界面；旧数据的名称兼容必须同时验证资源结构。
- 不把同名文件、同名材质或字符串前缀当作拥有权证明。多个候选且不能消歧时，停止修改并反馈原因。
- 跨场景复用必须是资源策略明确允许的行为。默认不修改其它场景独立实例的参数。

### `.blend` 读取计划

- 同一业务操作需要同一文件里的多类数据时，尽量合并到一次 `bpy.data.libraries.load()`。
- 在同一个上下文中检查入口是否存在，并填写 `target.collections/worlds/meshes/...`，避免先开一次探测、再开一次追加。
- 明确入口与必须显式加载的隐藏模板，让 Blender 追加正常依赖；不要把 `source` 中所有数据类型全部追加。
- 多个源文件按实际文件分组读取，不要求把所有资源强行合成一个大 `.blend`。
- 只有依赖都应共同追加时才合并；需要真正独立实例的导入，不得为了少一次读取而错误共享控制器或可变数据。

现有 `AppendTransaction.append_bundle(name, worlds=(), meshes=())` 在一次库读取中请求合集、World 和显式网格，返回根合集及两个按来源名称索引的字典；来源归属在返回前冻结。`append_collection(name)` 复用同一实现。生成式资产使用显式 `Creation.track()` 记录自行创建的 ID，不把全局新增差集当作拥有权。

示意，名称由具体资源决定：

```python
with bpy.data.libraries.load(path, link=False) as (source, target):
    # 在这里校验同一次请求需要的入口。
    target.collections = [root_name]
    target.worlds = [world_name]
    target.meshes = required_template_names
```

### 依赖与更新

- 在局部完成参数初始化、驱动重映射、节点和材质赋值，再发布到目标并做必要更新。
- 热循环优先直接操作 RNA，减少循环调用 `bpy.ops` 和每个对象一次 `view_layer.update()`。
- 遍历 `Collection.all_objects` 等原生集合并修改可见性、依赖、父级或结构前，先冻结为 `tuple`；相关写入可能使 Blender 的活动迭代器失效，不能边遍历边改写。
- 业务显式依赖更新应尽量集中在末尾；`bpy.ops` 自身可能执行更新，计时必须包含这部分开销，不能只测内部函数就宣称全部执行耗时。
- 普通 Python 字典可按需建立单次操作内的局部索引。只有实测需要时才添加跨操作缓存，并处理删除、重命名、Undo/Redo、文件切换及版本变更失效。
- 不通过关闭必要驱动、减少功能、覆盖用户参数或提高画质容差来制造“性能提升”。测试双方须说明实际功能范围。

## 4. 事务与清理

- 追加前的检查尽量完成于没有修改的阶段；追加后先验证，再链接合集、切换 World 或替换材质槽等。
- 修改已有数据前，记录本次将修改的字段或引用及其恢复方法，失败时逆序恢复。
- 只删除本次确认拥有的新增 ID。全工程“前后差集”可以帮助发现新增数据，但不是拥有权的充分证明：其它插件的导入/依赖图回调也可能创建数据。
- 尽量把新增依赖的记录限定在库追加/实例复制阶段，记录可确认的来源与依赖；不要等更新回调运行完才把所有新增 ID 一律算成自己创建的。
- 来源或拥有权无法确认时保守保留并报告，不做全局 orphan purge，不按名称批量删除，不删除用户已有数据。
- 清理只针对本次操作；用户已有数据引用和 Fake User 状态不得作为临时捷径任意修改。
- 失败事务由资源自身的恢复记录负责；原生撤销与执行接线引用 [Bus Skill 的 Blender 参考](../../oxal-bus/references/blender.md)。
- 替换已有部件时，先在旧 ID 仍存活的阶段完成所有可失败工作。`AppendTransaction.prepare_commit()` 完成排版及图片事务交接，`Creation.prepare_commit()` 完成排版、图片准备和拥有权登记；核验全部准备成功后才退役旧部件。退役后仅调用纯 Python 状态收尾的 `finish_commit()`，不再执行排版、IO 或可失败校验。普通 `commit()` 保留完整准备与收尾语义；提交后的无用数据清理由 `Creation.cleanup()` 处理，失败记录并延期，不回滚已退役数据。
- 已导入的数据属于用户工程，停用插件不自动删除。

持久实例的删除、重建及私有依赖替换使用 `util/ownership.py` 的精确登记。UUID/自定义标记会随 Blender 复制继承，不能单独证明拥有权：Scene 的根登记绑定实际根 ID，根登记再绑定实际数据 ID；整个根或子对象复制后不得自动接管。

- `seal_owned(root, proven_new_ids)` 只接收追加事务或显式创建记录；初次登记须包含新根且已发布到唯一场景，不能传全局差集或遍历得到的未知子项。成功替换可扩展已有有效根的登记。
- `require_owned(root, members)` 在破坏性操作前核验精确引用及唯一场景；缺失、继承或损坏的登记须拒绝，不从旧标记自动重建。
- 登记引用会增加一次 ID user。使用 `prune_owned(root)` 清理已登记的无用依赖，不按所有者标签全局扫描；用户 Fake User 和其它实际引用继续保留。
- 显式删除根前用 `release_owned(root)` 捕获已证明的 ID 并释放登记引用，再以 `remove_unused_owned(captured_ids)` 清理无用数据。登记后失败须恢复原登记和引用，追加失败须先释放新根登记再回滚。
- 原生形态键、嵌入节点等依赖按实际引用核对；实例之外的数据引用在删除前检查，避免保留用户副本却破坏其骨架/驱动引用。
- 已确认新增来源的所有者，其活动 Action、嵌入节点动画和 NLA（含 Meta strip）动作引用也须纳入追加归属；仍只接收本次新增候选，不能接管导入前已存在的用户 Action。
- Blender 删除 Mesh 等拥有者时可能同步释放其 Key。事务保留的 Python RNA 包装因此可能失效；删除、无用依赖清理和失败回滚必须先用 `util.resources.live_ids()` 过滤原记录，不能把失效包装传回 `batch_remove`。同批删除拥有者与其 Key 时由拥有者的原生生命周期处理 Key。
- `live_ids()` 只核验传入包装是否仍有效，不查找来源、不授予拥有权；仍须先按追加来源或显式创建记录确认删除范围。
- 注册的 RNA 属性可能保存在独立系统属性中，不能只用 `items()` 检查显式引用或重绑追加依赖。通过原生能力检测读取 `bl_system_properties_get()` 的原始存储，不调用其它插件的属性 getter；仅重映射当次来源已证明的 ID，遇到未映射 ID 应作为叶节点保留，不能递归改写外部数据。
- 场景显式引用核验排除已验证的 `ParticleEdit.object` 原生只读编辑缓存：Undo 后它可能保留先前姿态骨架，并非用户保存的显式场景引用。仅排除此精确入口，不跳过其它只读指针；原始自定义／系统存储中的实际引用仍须核验。

性能或保护测试可用全局差集发现异常增长，但不能把它转作业务来源证明或清理名单。

## 5. Bus 接入引用

Topic、EMT、参数/结果、回调、请求状态、登记/注销、调度及 Undo 桥统一遵循 [$oxal-bus](../../oxal-bus/SKILL.md)。
新增接入优先使用 Skill 中说明的现有端点；资源规范与模板不维护第二份 Bus API 或生命周期流程。

## 6. 统一计时口径

每个导入至少记录以下口径，并标明哪些阶段已计入总数：

| 指标 | 范围 |
| --- | --- |
| `submit_ms` | 提交 Operator 开始捕获参数到入队返回，不含排队、自动调度与业务执行时间 |
| `service_ms` | 业务工具进入到返回，含其内部更新 |
| `library_ms` | 库读取和追加整个上下文，不把上下文入口误当作追加已完成 |
| `prepare_ms` / `update_ms` | 主要准备阶段与显式依赖更新；不适用时可省略 |
| `dispatch_ms` | 总线实际执行端的整体耗时，含原生 Operator 与 Undo 开销 |
| `click_to_callback_ms` | 提交到结果回调，含排队与调度等待 |
| `source_reused` / `created` | 区分复用源数据与创建结果；从模板复制新实例可以同时为 true，不能把复用路径当首次加载数据 |

返回结果可额外带 `asset_id`、`asset_version`、实例标识和展示名称，不持有 RNA 对象。
不要求现在全部旧业务改成同一种结果类；新增业务使用明确的数据类，计时口径保持一致。

性能验证必须：

1. 分开测首次导入、重复操作和必要的实例创建；首次导入至少 5 个独立 Blender 进程，报告中位数与范围，注明 OS 磁盘缓存是否清空。
2. 与旧实现比较时使用相同源文件、选项、渲染设置和工作范围；功能裁剪另行列出，不混入同功能加速比例。
3. 至少覆盖小工程和代表性大工程，记录对象/材质/节点组等规模；重点检查全量扫描和 Undo 成本。
4. 检查重复操作的数据块数量与拥有权：激活应无重复增长；新实例应按计划增长，共享数据按约定复用。
5. 记录明显的主线程停顿或调度心跳间隔。调度配置和非抢占边界引用 Bus Skill，不将它们作为资源导入耗时保证。
6. 需要内存评估时区分 Python 分配、进程内存和渲染/GPU 资源；`tracemalloc` 不代表整个 Blender 内存。

没有统一的“所有资源必须小于 N 毫秒”门槛。以同等功能基线和资源规模判断；异常回退必须解释。

## 7. 接入验收

每个新资源导入按实际适用范围验证：

- 注册/绘制不打开资源，也不创建场景数据。
- 首次成功导入；文件缺失、入口缺失或格式损坏时的失败路径。
- 按声明策略验证重复激活、模板复用或创建新实例。
- 重命名、删除目标、目标场景变化、同名数据冲突及旧版本资源兼容。
- 多实例/多场景之间的独立参数和允许的共享关系。
- 纹理/外部依赖可用，驱动/材质/骨架等必要契约有效。
- 失败后已有场景和数据保留，只清理本次拥有的数据。
- 接入层验收按 Bus Skill；资源侧验证撤销/重做后的实例与依赖归属，以及保存重开后资源可用。
- 同等功能性能基线和代表性工程规模下的回归结果。

`.blend`、图片、外部模型、材质包等使用各自后端；复用这套流程和边界，不要求全部通过 `.blend` API。

## 8. 使用模板

[工具骨架](../assets/tool.py.example) 是工具流程骨架。其业务钩子由资源工具自己实现，未实现的钩子会明确失败。
复制到 `business/<domain>/<name>.py` 后声明身份、策略与作用域，实现资源读取、依赖处理和事务，再按 [Bus Skill](../../oxal-bus/SKILL.md) 完成通信与 Blender 入口接线。
模板不会自动执行；接入层具体步骤由 Skill 单独维护。

天空是已验证的具体参考，不是所有资源都应整段复制的业务实现。遇到第二种真实资源有相同基础需求时，再提取有实测依据的共用函数。

目前人模和物品栏已经接入，可参考 [人模工具](../../../../business/human/human.py)、[物品栏工具](../../../../business/inventory/inventory.py)、[模块登记](../../../../module/__init__.py)和 [资源 Operator](../../../../operation/resources.py)。
它们共用 [util/resources.py](../../../../util/resources.py) 的单次追加与来源归属事务；端点及 Undo 接线引用 [Bus Skill 的 Blender 参考](../../oxal-bus/references/blender.md)。
这两个后端按 `NEW_INSTANCE` 每次重新追加一套可编辑依赖，明确报告 `source_reused=False, created=True`，不把可能修改过的用户实例作为缓存模板。
资源行为与计时按实际任务验证；临时脚本和输出按 AGENTS.md 的 `_test` 后缀规则命名，按需创建、用完清理，不随 Git 分发。骨架用于设计流程，实际接入以现有业务实现为参考。结果在对话中说明，不假定已有测试脚本存在，也不生成独立 Markdown 报告。
